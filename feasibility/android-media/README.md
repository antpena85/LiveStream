# M2 camera/audio media experiment

Operator-initiated ten-second local capture on the two authorized phones. This
evaluates the proposed [RootEncoder 2.8.1](https://github.com/pedroSG94/RootEncoder)
Camera2 → GL scoreboard → AVC path and microphone → AAC path. RootEncoder's
[Apache-2.0 license](https://github.com/pedroSG94/RootEncoder/blob/master/LICENSE.txt)
and resolved dependencies still belong to the final stack/license review.
It is a diagnostic candidate, not the release application or a v1 recording feature.

To open this isolated project in Android Studio, select this directory—the one
containing `settings.gradle.kts`—with **File → Open**. Use the project-local
JDK/Gradle/SDK and M2-only scope described in the root
[Android Studio workflow](../../ANDROID_STUDIO.md). Do not combine this project
with the inventory project or treat IDE import as a release-stack decision.

[Contract specified before execution](../../plan/specifications/m2-media-check-contract.md).
The readiness source is generated by copying the exact JVM-tested
`StreamSession.kt`, using AGP's Kotlin generated-source API. Do not edit the
generated file. [Built-in Kotlin guidance](https://developer.android.com/build/migrate-to-built-in-kotlin).

From the workspace root:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/m2/run-android-inventory.ps1 -Probe media assembleDebug
powershell -NoProfile -ExecutionPolicy Bypass -File tools/m2/device-capability-probe.ps1 -Probe media -Action Install
```

On each phone, use **M2 Camera and Audio Test**, tap **Run 10-second camera/audio
test**, and grant camera/microphone access if prompted. Point the phone at a
test scene and speak during capture. It stops automatically; leaving the
activity interrupts the test. The clip stays in this app's private storage.
The next test replaces the prior diagnostic clip. No destination is configured
and this activity never calls `startStream`.

Use **Review clip** and **Decoded frame** to check orientation, complete fixture
values (ABC 99/S2/T/O2/serve and XYZ 100/S1/T/O1), readability and audible audio.
Metadata alone cannot establish those human/received-output observations.

After a completed run, collect only metadata:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/m2/device-capability-probe.ps1 -Probe media -Action Collect
```

The report lists requested settings, actual tracks/sample counts/timestamps,
observed audio input types and decoded-frame availability. The collector does
not pull the clip, frame image or personal scene/audio content. Trial values
are 1280×720/30, 2 Mbps video and stereo 48 kHz/128 kbps AAC, with a hardware
video/software audio mode requested for this experiment. Actual results must
be read before claiming support; preferred input is distinct from actual route.

The microphone readiness case has an observed red/green cycle at confirmed
T02. The unmeasured camera/encoder path is an exploratory hardware experiment;
building the APK is not a successful capture or broadcast result. Other lens
changes, quality adaptation, thermal/lifecycle stress, remote topology and
provider/network checks remain separate M2 work.

## Front/rear camera and mute experiment

The separate **Run 20-second switch/mute test** button starts an operator-approved
local capture using the same fixture. Speak/count throughout: microphone mute is
requested at 4 seconds, unmute at 8, front camera at 12 and rear camera at 16.
The test stops at 20 seconds. Review the entire clip for live/silent/live audio,
both scene changes, stable scoreboard, orientation and visible interruptions.
This is front/rear switching, not a test of every physical rear lens.

The report adds `experiment`, timed `controlEvents` and any `controlError`.
Reported mute state/camera IDs are API observations, not proof of the encoded
result. A new run replaces the private clip. Collect to a distinct directory
such as `plan/evidence/m2/android-media-transitions-2026-10-24` to preserve the
baseline metadata. Do not collect the scene or audio recording.

This extension is an exploratory hardware adapter, not a new JVM behavior or a
claimed TDD cycle. The existing JVM regression suite currently executes 13 tests
(ten storage and three readiness cases); older twelve-test counts are historical.
