# M2 camera/audio media experiment

Operator-initiated ten-second local capture on the two authorized phones. This
evaluates the proposed [RootEncoder 2.8.1](https://github.com/pedroSG94/RootEncoder)
Camera2 → GL scoreboard → AVC path and microphone → AAC path. RootEncoder's
[Apache-2.0 license](https://github.com/pedroSG94/RootEncoder/blob/master/LICENSE.txt)
and resolved dependencies still belong to the final stack/license review.
It is a diagnostic candidate, not the release application or a v1 recording feature.

To open this isolated project in Android Studio, select this directory—the one
containing `settings.gradle.kts`—with **File → Open**. Use the project-local
JDK/Gradle/SDK and M2-only scope described in the root
[Android Studio workflow](../../ANDROID_STUDIO.md). Do not combine this project
with the inventory project or treat IDE import as a release-stack decision.

[Contract specified before execution](../../plan/specifications/m2-media-check-contract.md).
The local capture permission gate is generated by copying the JVM-tested
`LocalCaptureReadiness.kt`, using AGP's Kotlin generated-source API. Do not edit
the generated file. This local-only gate never authorizes publishing; the separate
`StreamSession` retains its pending-stop and numeric-fit requirements. The
shared session, manual publisher control, and read-only safety-state interface
are compiled here to check source compatibility, but the activity does not use
them for publishing. The activity uses an isolated Android SQLite safety-store
experiment for its local diagnostic scores, not for a publisher. Separate session reads do not
establish atomicity or safe publishing.
An `AndroidPublisherAdapter` now binds the shared manual control to the
candidate `GenericStream` start/stop methods, but deliberately denies all
starts because an assessed broadcast-fit and durable stop-recovery path are
not yet integrated. During local capture the activity instantiates the adapter
and forwards sanitized connection events, and offers a no-network diagnostic
fit preflight. The activity exposes no publisher Start control. These callbacks
are not proof of network integration or stop confirmation; it is not a working
broadcast or a trial-ready build.
Each local capture now binds callback delivery to its own adapter instead of
looking up whichever adapter happens to be current when a delayed event arrives.
The diagnostic fit preflight reads the displayed two-team fixture and its
revision together in one SQLite query before measuring the text. That snapshot
does not include a full scoreboard or authorize the publisher.
[Built-in Kotlin guidance](https://developer.android.com/build/migrate-to-built-in-kotlin).

## Android safety-store experiment

`AndroidSafetyStore` implements the probe safety interface using Android SQLite.
The local-only score buttons and encoded overlay now read and update a separate
durable diagnostic database. Scores persist across local captures and activity
restarts; this is not a match reset or a broadcast-ready scoreboard. The
instrumented check verifies both team scores after reopening, not the activity
UI or the encoded video. Local capture stops if an update or redraw fails.
The instrumented check writes an actual team score and pending stop in one
transaction, closes and reopens the database, and verifies the updated score
and that the session blocks Start. The activity does not yet invoke this
combined operation or assess fit. Its points-only
fixture is not a complete match, and the experiment does not implement fit
measurement, publisher stop/confirmation, receipt deduplication or recovery.
The store also supports clearing a specific pending-stop marker after an
independently confirmed stop. No real publisher callback is wired to that
operation; a stop request or local streaming flag is not confirmation.
An experimental session claim checks the assessed revision and existing markers
in one transaction and leaves a durable marker before any publisher call.
The activity and adapter do not yet use that claim; it does not confirm a stop.
`DiagnosticPublisherLifecycle` separately demonstrates in-memory ownership of
that claim: only the matching callback can mark it connected, and a new lifecycle
cannot claim while the previous marker remains. Its controllable diagnostic
publisher boundary now invokes connect only after a durable claim and dispatches
a confirmed stop without clearing the marker. It is not wired to the real
publisher and does not reconcile a real shutdown.
If the diagnostic connect operation throws, the lifecycle requests cleanup and
retains the marker in `Stopping`; it does not expose the thrown message.

Build with the media runner using `assembleDebug assembleDebugAndroidTest --offline`.
After checking ADB authorization, install both debug APKs from
`build/outputs/apk/debug/` and `build/outputs/apk/androidTest/debug/` on the
chosen device, then run:

```powershell
adb -s <device-serial> shell am instrument -w livestream.feasibility.mediaprobe.test/livestream.feasibility.mediaprobe.SafetyStoreInstrumentation
```

Check the reported `result=PASS` and instrumentation code `-1`; ADB command
success alone does not establish a passing test. The test deletes only its own
diagnostic database. No camera, microphone or network publishing is exercised.

**Check test destination (no broadcast)** opens a temporary format-only dialog.
Use fictional values during testing: it checks RTMP(S), a host, and a nonblank
key, but does not verify a service, save a destination, connect, or authorize
publishing. Embedded URL user-info is rejected; other URL forms and provider
compatibility remain unverified. Do not enter real credentials for this check.
On 2026-11-01 the debug APK was installed and opened on an authorized Pixel 10
Pro XL. An ADB-driven check with a fictional RTMPS address and fictional key
displayed the basic-format-accepted message; a check without a key displayed
the missing-key message. This is a UI smoke check, not proof of destination
reachability, credential security, publishing, or received media.

From the workspace root:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/m2/run-android-inventory.ps1 -Probe media assembleDebug
powershell -NoProfile -ExecutionPolicy Bypass -File tools/m2/device-capability-probe.ps1 -Probe media -Action Install
```

On each phone, use **M2 Camera and Audio Test**, tap **Run 10-second camera/audio
test**, and grant camera/microphone access if prompted. Point the phone at a
test scene and speak during capture. It stops automatically; leaving the
activity interrupts the test. The clip stays in this app's private storage.
The next test replaces the prior diagnostic clip. No destination is configured
and this activity never calls `startStream`.

During the 10-second local test, **+ ABC** and **+ XYZ** update a simplified
diagnostic score. Use **Review clip** to inspect whether both updates appear in
the encoded video, and check orientation and audible audio. The 20-second
switch/mute test retains the asymmetric fixture (ABC 99/S2/T/O2/serve and XYZ
100/S1/T/O1). **Decoded frame** shows a single frame, not the whole sequence.
The simplified score is not match logic and must not be used for a broadcast
or real match. Its local renderer measures the diagnostic text and widens its
bitmap within a provisional limit; if it still cannot fit, the saved score is
retained and local capture stops with a notice. This is not the full numeric-fit
or publishing-stop safety contract: only the diagnostic fixture is measured,
and readable size, safe bounds and encoded output remain unreviewed.
Metadata alone cannot establish those human/received-output observations.

After a completed run, collect only metadata:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/m2/device-capability-probe.ps1 -Probe media -Action Collect
```

The report lists requested settings, actual tracks/sample counts/timestamps,
observed audio input types and decoded-frame availability. The collector does
not pull the clip, frame image or personal scene/audio content. Trial values
are 1280×720/30, 2 Mbps video and stereo 48 kHz/128 kbps AAC, with a hardware
video/software audio mode requested for this experiment. Actual results must
be read before claiming support; preferred input is distinct from actual route.

The microphone readiness case has an observed red/green cycle at confirmed
T02. The unmeasured camera/encoder path is an exploratory hardware experiment;
building the APK is not a successful capture or broadcast result. Other lens
changes, quality adaptation, thermal/lifecycle stress, remote topology and
provider/network checks remain separate M2 work.

## Front/rear camera and mute experiment

The separate **Run 20-second switch/mute test** button starts an operator-approved
local capture using the same fixture. Speak/count throughout: microphone mute is
requested at 4 seconds, unmute at 8, front camera at 12 and rear camera at 16.
The test stops at 20 seconds. Review the entire clip for live/silent/live audio,
both scene changes, stable scoreboard, orientation and visible interruptions.
This is front/rear switching, not a test of every physical rear lens.

The report adds `experiment`, timed `controlEvents` and any `controlError`.
Reported mute state/camera IDs are API observations, not proof of the encoded
result. A new run replaces the private clip. Collect to a distinct directory
such as `plan/evidence/m2/android-media-transitions-2026-10-24` to preserve the
baseline metadata. Do not collect the scene or audio recording.

This extension is an exploratory hardware adapter, not a new JVM behavior or a
claimed TDD cycle. The existing JVM regression suite currently executes 13 tests
(ten storage and three readiness cases); older twelve-test counts are historical.
